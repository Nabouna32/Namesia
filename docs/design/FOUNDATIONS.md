# Fondations visuelles — Namesia

- **Version :** 1.0
- **Mis à jour le :** 2026-11-27 20:01:15 (Europe/Paris)


Consulter aussi le [système de design](../DESIGN-SYSTEM.md) et la [vérification Material 3](../MATERIAL-3-VERIFICATION.md).

## 1. Direction

Namesia adopte **Material 3**, avec une palette générale **Fidelity** et une palette complémentaire **Rainbow** réservée aux éléments éditoriaux qui bénéficient d'une différenciation chromatique. L'interface vise la sensation d'une application Pixel : composants familiers, surfaces tonales, formes cohérentes, interactions réactives et navigation adaptative.

Ce choix est une référence de conception et de comportement, pas une prétention à reproduire le système Android natif ou ses barres système. Le navigateur conserve ses conventions, ses capacités et ses limites.

Les composants de `components/material3/` sont des ports Web React/HTML des contrats AndroidX, pas des composants Compose importés dans Next.js. Material Web (`@material/web`) a été évalué comme alternative officielle ; son état source épinglé confirme une maintenance sans nouvelles fonctionnalités planifiées et une couverture stable incomplète pour le shell et les composants utilisés par Namesia. Le projet conserve donc une seule pile React/HTML, avec les noms et contrats AndroidX vérifiés ; aucun mélange de bibliothèques ni composant de laboratoire n'est introduit. Voir [ADR-0037](../decisions/ADR-0037-architecture-composants-material3.md).

La marque Namesia utilise les rôles Fidelity, y compris pour son monogramme. Les couleurs Rainbow générées par Material Color Utilities servent uniquement aux catégories éditoriales identifiées (notamment les associations symboliques) : elles ne sont jamais attribuées selon l'ordre, la position, le hasard ou le prénom lui-même. Elles ne remplacent ni les rôles fonctionnels Fidelity ni les couleurs sémantiques success/warning/info. Les titres, les actions, les surfaces générales et les repères de navigation restent Fidelity ; Rainbow n'est pas un dégradé décoratif appliqué aux textes ou aux fonds de page. Les états de succès, d'avertissement et d'information conservent leurs couleurs sémantiques comme couleurs personnalisées M3 distinctes des rôles système.

## 2. Source de vérité des couleurs

La palette est calculée avec la bibliothèque officielle Google **`@material/material-color-utilities`**. `lib/material-theme.ts` est l’unique générateur : il calcule les schémas clair et sombre et produit les déclarations CSS intégrées au `<head>` dès le rendu serveur. La règle CSS `@media (prefers-color-scheme: dark)` applique directement le schéma sombre et suit les changements de préférence sans JavaScript, hydratation ni synchronisation DOM. Le CSS des composants ne contient donc aucune palette de secours indépendante. Le thème est construit avec :
- couleur source primaire : `#0B57D0`, bleu Google `baseline_primary_600` documenté dans le thème Android de Chromium. C'est un choix explicite de source Namesia, pas une affirmation selon laquelle le bleu serait la baseline AndroidX Material 3 : celle-ci conserve le violet `#6750A4`. Fidelity calcule les rôles à partir du bleu source, qui n'est jamais recopié directement dans les composants. Le résultat reste la variante Fidelity demandée, pas un schéma statique Tonal Spot ;
- variante du thème d'interface : `Variant.FIDELITY` ;
- variante complémentaire des catégories : `Variant.RAINBOW`, calculée séparément avec la même couleur source ;
- bibliothèque de calcul : `@material/material-color-utilities` version `0.4.0`, épinglée dans `package-lock.json` et dans [Vérification Material 3](../MATERIAL-3-VERIFICATION.md) ;
- version d'algorithme : `specVersion: "2021"`, version de `ColorSpec` dans Material Color Utilities ; ce n'est pas une version de Material Design 3 ni une référence à l'ancien système de composants. Le code de la bibliothèque maintient Fidelity et Rainbow sur 2021 : la spécification 2025 n'est transmise qu'aux variantes Expressive, Vibrant, Tonal Spot et Neutral ;
- plateforme MCU : `phone`, paramètre de calcul du schéma correspondant à la cible Android mobile, sans accès aux API Android depuis le navigateur ;
- niveau de contraste standard : `0` ;
- schémas clair et sombre recalculés selon `prefers-color-scheme`.

Le générateur expose les rôles système sous leurs noms M3 exacts `--md-sys-color-*`. Les rôles absents provoquent une erreur explicite : aucun rôle n’est silencieusement ignoré. Le rendu initial et les changements de préférence proviennent du même CSS généré côté serveur, sans palette statique approximative, hydratation ni bascule visuelle vers une autre variante.

La couleur source est fixe et maîtrisée par Namesia : le navigateur n'a pas accès au fond d'écran Android et le site ne prétend donc pas récupérer la couleur dynamique du téléphone. Une future personnalisation de la couleur source doit rester une décision explicite, pas une collecte implicite.

### Rôles Material

Les composants consomment les rôles du schéma, jamais des couleurs arbitraires :
- `primary`, `on-primary`, `primary-container`, `on-primary-container` : action principale et sélection ;
- `secondary` et ses conteneurs : navigation et actions secondaires ;
- `tertiary` et ses conteneurs : accent complémentaire ;
- `surface`, `surface-container-low`, `surface-container`, `surface-container-high`, `surface-container-highest` : plans et hiérarchie des surfaces ;
- `on-surface`, `on-surface-variant`, `outline`, `outline-variant` : texte et contours ;
- `error` et ses conteneurs : erreurs.

Les composants consomment directement les rôles `--md-sys-color-*` et, pour les seules extensions explicitement définies, `--namesia-color-*`. Aucun alias applicatif générique `--color-*`, `--ink`, `--muted` ou `--line` n'est admis. Material 3 ne définit pas `success`, `warning` et `info` parmi ses rôles système de base. Il prévoit toutefois l'extension d'un schéma par des couleurs personnalisées et leurs quatre rôles tonals. Namesia conserve les sources sémantiques éprouvées `success` (`#386A20`), `warning` (`#795900`) et `info` (`#005B9A`) ; `customColor` de Material Color Utilities génère pour chacune `color`, `onColor`, `colorContainer` et `onColorContainer` en clair et sombre. Ces extensions portent exclusivement le préfixe `--namesia-color-*` et ne sont jamais présentées comme des rôles système. Les erreurs utilisent les rôles M3 `error`. Aucune valeur de secours n'est autorisée dans `var()` : une donnée de thème absente doit rester visible comme défaut de contrat.

### Signature Rainbow

Les catégories utilisent trois familles de rôles tonals issues du schéma `Variant.RAINBOW` (`--namesia-color-category-1` à `--namesia-color-category-3`, avec leurs conteneurs et couleurs de premier plan). Une catégorie reçoit toujours la même teinte, quelle que soit la fiche ou l'ordre d'affichage. Une carte de prénom, un bouton ou une surface fonctionnelle ne constitue pas une catégorie : elle utilise les rôles Fidelity neutres ou sémantiques. Les titres, les accents typographiques et les fonds de page ne reçoivent pas de dégradé Rainbow. Les cartes d'associations peuvent recevoir une légère teinte stable issue de la catégorie, sur une surface Fidelity ; leur contour et leur badge utilisent respectivement la teinte et le rôle `on-container` de cette même catégorie, jamais un rôle tertiary générique. La vitrine « Les prénoms à découvrir » applique une surface neutre identique à ses cartes ; aucune carte ne reçoit primary, secondary ou tertiary selon sa position. Les variations de mise en page suivent la largeur disponible : trois colonnes à partir de 840 px (fenêtres expanded), deux de 600 à 839 px (medium) et une sous 600 px (compact).

## 3. Formes, typographie et élévation

- Typographie : Roboto pour tous les rôles, des titres aux contrôles et au corps, y compris le champ JSON de l'administration qui utilise `body-medium` plutôt qu'une police monospace concurrente. La police est chargée au build par `next/font/google`, auto-hébergée sur le domaine Namesia et préchargée ; `display: block` et `adjustFontFallback: false` empêchent l'ajout d'une police de substitution ; le navigateur ne contacte pas Google. Les sous-ensembles `latin` et `latin-ext` couvrent les textes français. Les graisses 400 et 500 sont chargées ; aucune police de substitution ni pile générique n’est définie. Le corps courant reste à 16 px.
- Échelle Material 3 : display large/medium/small 57/64, 45/52 et 36/44 px ; headline large/medium/small 32/40, 28/36 et 24/32 px ; title large/medium/small 22/28, 16/24 et 14/20 px ; body large/medium/small 16/24, 14/20 et 12/16 px ; label large/medium/small 14/20, 12/16 et 11/16 px. Les graisses sont strictement 400 et 500. Les libellés ne sont pas forcés en capitales. Chaque rôle possède ses tokens `--md-sys-typescale-*` de famille, taille, graisse, interligne et approche. Tous les textes utilisent l'interligne et l'approche du rôle correspondant, sans valeurs locales qui créent une échelle concurrente. Seuls les glyphes décoratifs surdimensionnés (initiale de vitrine et monogramme de fiche) conservent une boîte de ligne volontairement resserrée ; ils ne portent aucun contenu textuel.
- Les boutons (`Button`) et filtres sélectionnables (`FilterChip`) utilisent intégralement le rôle `label-large` : famille, taille, graisse, interligne et approche. La taille seule ne suffit pas à identifier un rôle typographique ; les variantes métier ne doivent pas remplacer ce rôle par un style `body`. Le Button AndroidX 1.5.0 dessine un conteneur de 40 dp (`ButtonSmallTokens.ContainerHeight`) dans une cible Web de 48 px, avec une largeur minimale de 58 dp, 24 dp de padding horizontal et 12 dp pour TextButton. Les icônes de Button font 18 dp (`ButtonDefaults.IconSize`) et celles d’IconButton 24 dp (`SmallIconButtonTokens.IconSize`). IconButton est une primitive distincte : cible interactive de 48 dp, conteneur visuel circulaire transparent de 40 dp (`SmallIconButtonTokens.ContainerHeight` et `ContainerShapeRound`), contenu 24 dp et couches d’état dans le cercle de 40 dp. `iconButtonColors()` hérite de `LocalContentColor` et applique 38 % de cette couleur à l’état désactivé ; `iconButtonVibrantColors()` utilise les tokens `OnSurfaceVariant` et `OnSurface` à 38 %. Le port Web hérite donc de la couleur du contexte, tandis que SearchBar définit explicitement `on-surface-variant` pour son action d’effacement. Son CSS Module reste isolé de Button. OutlinedButton utilise `outline-variant` et `on-surface-variant` ; TextButton utilise `primary` conformément à l'implémentation AndroidX. Les états désactivés utilisent 10 % pour le conteneur Filled/Tonal (et pour le contour Outlined) et 38 % pour le contenu. L’état pressé de Button adopte `corner-small`. Le `FilterChip` AndroidX 1.5.0 a un conteneur visuel de 32 dp (`FilterChipTokens.ContainerHeight`) ; sa cible tactile reste de 48 dp. L’adaptateur Web conserve un bouton natif de 48 px et dessine la capsule de 32 px dans cette cible, sans agrandir artificiellement la surface.
- Le champ de recherche (`SearchBar`) utilise un conteneur replié de 56 dp, une forme `full`, la couleur `surface-container-high` et le rôle `body-large` pour la saisie. L’icône initiale utilise `on-surface`, l’action finale `on-surface-variant`. Le champ garde un libellé HTML accessible même si seul le placeholder est visible. L’expansion native de SearchBar n’est pas reproduite : Namesia présente les résultats dans le flux de la page.
- Les espacements suivent une grille de 4 px, avec les pas de 8 px privilégiés. Les rayons utilisent les tokens `--md-sys-shape-corner-*`, sauf Checkbox : AndroidX définit explicitement son indicateur par `RoundedCornerShape(2.dp)`, sa couche d'état par un cercle de 40 dp (`StateLayerShape = CornerFull`) et son anneau de focus par une forme 25 % de 40 dp, colorée `Secondary`. Ces géométries sont conservées dans son module isolé et vérifiées contre `CheckboxTokens.kt`.
- Formes : extra-small 4 px, small 8 px, medium 12 px, large 16 px, extra-large 28 px et full/pill.
- Élévation : hiérarchie tonale des surfaces en priorité ; aucune ombre CSS décorative n’est conservée. Les ombres ne sont utilisées que lorsqu’un composant AndroidX définit explicitement un niveau : Button et FilledTonalButton appliquent le niveau 1 au survol sur leur capsule visuelle ; ElevatedCard utilise le niveau 1 au repos, le niveau 2 au survol et revient au niveau 1 à la pression ; FilledCard et OutlinedCard restent au niveau 0 au repos, passent au niveau 1 au survol et reviennent au niveau 0 à la pression. Les couches pressées des cartes utilisent `on-surface`, conformément au contenu AndroidX, jamais `primary`. Le rôle système `shadow` est utilisé pour la traduction Web. Les niveaux M3 `--md-sys-elevation-level0` à `level5` restent des valeurs dp et ne sont pas directement des valeurs `box-shadow` ; la traduction Web est localisée dans le composant et documentée.
- Densité : cibles tactiles d'au moins 48 × 48 px lorsque l'espace le permet ; les éléments visuels peuvent être plus petits à l'intérieur de leur cible.

### Accueil

Les titres de section et leurs liens d'action forment un groupe lisible : sur grand écran, le lien reste aligné au titre ; sous 600 px, il passe sur sa propre ligne, sous le titre, sans comprimer celui-ci. Le lien conserve une cible tactile minimale de 48 px. Le hero sépare le message éditorial et les outils de découverte : introduction à gauche et panneau de recherche à droite à partir de 840 px (expanded), puis empilement naturel sur les fenêtres compactes et medium. Le panneau utilise une surface Fidelity distincte, un contour discret et un titre explicite ; la recherche et la découverte aléatoire y forment un seul point de départ. Le texte descriptif utilise `on-surface-variant`, jamais la couleur primaire comme simple décoration. La mention de génération par IA reste visible dans le panneau, au même endroit que les outils auxquels elle se rapporte. Les cartes vedettes gardent une hauteur minimale plutôt qu'une hauteur rigide ; les noms longs peuvent revenir à la ligne sans pousser l'action de découverte hors de la carte. Les cartes du catalogue appliquent la même règle de retour à la ligne.

### Fiche de prénom

La fiche est un parcours de lecture : son introduction et ses rubriques utilisent le premier plan `on-surface`, avec l'échelle body large 16/24 px. Les libellés de rubrique et les métadonnées utilisent les rôles label/body adaptés, sans capitales forcées. Le sommaire est composé de liens natifs présentés comme des chips tonales outlined de 48 px de haut, avec états hover réservés aux pointeurs fins, pression tactile et focus clavier visible. Les ancres ménagent 88 px au-dessus de chaque rubrique pour que le titre reste visible sous la barre supérieure fixe. Les surfaces du hero, de la note éditoriale et de la découverte utilisent directement les rôles Fidelity dans leurs règles de base ; aucune couche tardive ne redéfinit ces composants.

## 9. Références et limites de fidélité

Material 3 Fidelity constitue la base forte de Namesia : lorsqu'un composant ou motif M3 peut être porté proprement en React/HTML, il est le choix par défaut. Le projet ne revient pas à un thème générique ou à des composants standard moins fidèles pour gagner quelques lignes de code. Les adaptations Web nécessaires (sémantique HTML, clavier, focus, responsive, accessibilité) préservent autant que possible l'identité M3. Tout écart significatif est justifié par un besoin concret, documenté avec ses options et conséquences, puis reste réexaminable ; aucune exception ne fige l'architecture contre une meilleure solution future.


La spécification [Material Design 3](https://m3.material.io/) est la référence normative pour les rôles, les composants, l'anatomie, les états et les comportements. Les sources AndroidX Jetpack Compose Material 3 (`androidx/compose/material3`) sont la référence d'implémentation concrète : API `MaterialTheme`/`ColorScheme`, valeurs baseline et implémentation des composants standards. Les sources AndroidX sont consultées pour reproduire les mêmes noms, variantes, dimensions et états ; elles ne sont pas importées dans Next.js, car Compose est une implémentation Kotlin/Android. Le Web traduit ces contrats en React et HTML natif. Material Color Utilities est la source de l'algorithme Fidelity/Rainbow et des couleurs personnalisées. La version `2021` citée plus haut concerne uniquement son algorithme ColorSpec. Le système visuel Namesia reste Material 3 standard, pas Material 3 Expressive.

Le registre des rôles, les sources officielles, les vérifications automatisées et les exceptions Web sont détaillés dans [Vérification Material 3](../MATERIAL-3-VERIFICATION.md). La navigation, les icônes et les surfaces du site sont des implémentations Web accessibles des modèles Material. Le Web ne peut pas reproduire les gestes système, les barres système transparentes, le retour prédictif Android, les animations natives exactes ni l'extraction du fond d'écran. Ces éléments ne doivent pas être simulés de manière trompeuse.
